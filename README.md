````
# WayFinder — Real-Time AI Travel Intelligence Platform

WayFinder is a production-style AI travel planning platform that generates personalized, real-time, budget-aware, weather-aware, location-aware, and safety-aware travel plans.

The system combines a custom LangGraph workflow, LangChain tools, city-guide RAG, real places discovery, live weather, live news, dynamic budget estimation, and travel risk analysis to generate practical travel itineraries.

---

## 1. Project Overview

Travel planning usually requires users to switch between multiple apps for weather, places, local updates, budget planning, safety information, and itinerary creation.

WayFinder solves this problem by providing a single AI-powered travel planning experience.

Users can enter:

- Destination
- Number of days
- Number of travelers
- Budget
- Travel style
- Food preference
- Interests such as nightlife, cafes, shopping, beaches, history, pubs, clubs, or family travel

The backend then runs a controlled AI workflow and returns a structured travel plan.

Example request:

```json
{
  "destination": "Hyderabad",
  "days": 2,
  "travelers": 2,
  "budget": 12000,
  "travel_style": "comfort",
  "food_preference": "mixed",
  "source_city": "Vijayawada",
  "interests": ["clubs", "pubs", "cafes", "nightlife"],
  "news_required": true,
  "news_limit": 5,
  "risk_check": true
}
````

## 2. Core Features

### Personalized Travel Planning

WayFinder creates itineraries based on user-selected interests instead of producing generic tourist recommendations.

Examples:

* If interests include `clubs`, `pubs`, and `nightlife`, the system prioritizes nightlife zones, cafes, lounges, safe late-night travel, and venue verification.
* If interests include `history`, it prioritizes monuments, forts, museums, and heritage routes.
* If interests include `shopping`, it prioritizes markets, malls, local shopping streets, and budget buffers.
* If interests include `beaches`, it prioritizes beach areas, shacks, sunset points, and safety precautions.

---

### City Guide RAG

The system uses Retrieval-Augmented Generation to retrieve curated city guide data from local text files.

Stored city guides are available for:

* Hyderabad
* Bengaluru
* Chennai
* Goa
* Mumbai

The city guides include:

* City overview
* Best areas to stay
* Historical places
* Nightlife, clubs, pubs, lounges, and bars
* Cafes
* Food
* Shopping
* Transport
* Safety
* Budget notes
* Suggested itineraries

The RAG layer helps the LLM generate more grounded and city-specific recommendations.

---

### Real Places Discovery

If the selected city is not present in the local city guides, or if the user asks for highly specific interests, the system uses a real places discovery tool.

The current implementation uses:


This allows the system to discover real places such as:

* Cafes
* Restaurants
* Pubs
* Bars
* Nightclubs
* Museums
* Shopping places
* Hospitals
* Pharmacies
* Beaches
* Religious places

This prevents the system from depending only on generic LLM knowledge.

### Dynamic Budget Planning

The budget planner is not directly generated by the LLM.

It is calculated using a deterministic Python budget tool that considers:

* Destination
* City cost profile
* Travel style
* Number of days
* Number of travelers
* Food preference
* User interests
* Discovered real places
* Place categories
* City guide availability
* Location-specific cost multiplier

The budget output includes:

* Low, expected, and high estimate
* Category-wise cost breakdown
* Daily budget allocation
* Budget status
* Budget gap
* Cost drivers
* Saving plan
* Recommendations
* Confidence score

Example output:

```json
  "total_estimate": {
    "low": 16000,
    "expected": 18800,
    "high": 23500
```

The system calls a weather API to retrieve current destination weather.

Weather data is used to adjust the final itinerary and travel tips.

For example:

* If the weather is hot, the system recommends morning/evening outdoor activities.
* If rain is expected, it recommends indoor alternatives, cafes, malls, or flexible travel.
* If weather data is unavailable, the system clearly mentions the limitation.

## 5. Backend Workflow

The backend uses a custom `StateGraph`.

The graph is intentionally controlled and linear for reliability:

```text
START
  ↓
router_node
  ↓
weather_node
  ↓
city_guide_node
  ↓
places_discovery_node
  ↓
budget_node
  ↓
news_fetch_node
  ↓
news_analysis_node
  ↓
risk_analysis_node
  ↓
llm_planner_node
  ↓
END
```

The router node decides which tools are needed using LLM-based routing flags.

Each node checks its router flag before running.

This gives the project both:

* Controlled production-style execution
* LLM-guided tool selection

---

## 6. Why Custom StateGraph Instead of ReAct Agent?

The project does not use `create_react_agent`.

Instead, it uses a custom LangGraph `StateGraph`.

Reason:

* More control over workflow order
* Better reliability
* Easier debugging
* Predictable tool execution
* Better for production workflows
* Avoids uncontrolled ReAct loops
* Works well with structured frontend input

The system still uses actual LangChain tools with `@tool`.

## 20. How Accuracy Is Improved

WayFinder improves accuracy using multiple layers:

### 1. Interest-aware RAG

The city guide retriever uses interests to fetch relevant chunks.

Example:

```text
clubs, pubs, nightlife
```

retrieves nightlife sections instead of generic sightseeing sections.

---

### 2. Real Places Discovery

If city guides are missing or weak, OpenStreetMap places are used.

This helps with unknown cities like:

```text
Pune
Delhi
Kochi
Jaipur
Mysuru
```

---

### 3. Strict Final Prompt

The final prompt instructs the LLM to:

* Avoid hallucinating places
* Use tool outputs only
* Prioritize interests
* Respect budget output
* Mention missing data
* Avoid generic tourist plans when interests are specific

---

### 4. Final Response Validation

The backend validates and repairs the LLM response.

It ensures:

* Required days are present
* Budget warning is added when needed
* Safety tips are added for medium/high risk
* Nightlife plans do not fall back to generic monuments
* Missing city guide limitations are clearly mentioned

## 24. Design Decisions

### Why use StateGraph?

StateGraph provides controlled orchestration.

It avoids unpredictable agent loops while still allowing intelligent routing.

---

### Why use tools?

Tools separate business logic from the LLM.

The LLM should not directly invent:

* Weather
* Budget
* Places
* News
* Risk

Instead, tools generate structured data, and the LLM converts that into a useful response.

---

### Why use RAG?

RAG provides curated local knowledge.

It is better than relying only on the LLM’s general knowledge.

---

### Why add Places API?

RAG only works for cities present in the local city guide database.

Places discovery helps unknown cities and interest-specific searches.

---

### Why not let the LLM calculate budget?

LLMs can hallucinate prices.

The project uses a deterministic budget tool for explainable and safer estimates.

---

## 25. Current Limitations

* OpenStreetMap may not include ratings, reviews, photos, or full opening hours.
* Budget is still an estimate, not real-time pricing.
* News API results depend on API availability and query quality.
* Weather API may fail for ambiguous city names.
* RAG quality depends on how detailed the city guide files are.
* OpenStreetMap place data may be incomplete for some locations.
* Hotel and transport prices are not fetched from live booking APIs yet.
